# IPMATS — DPWH 360° Infrastructure Project Monitoring and Transparency System

IPMATS tracks DPWH infrastructure projects in Occidental Mindoro (Region IV-B MIMAROPA). DPWH personnel record each project, its construction phases, progress reports, finances, 360° site photos and supporting documents. The system checks every project automatically and gives it a Green / Yellow / Red flag with reasons, auditors review those flags and record findings, and the public can browse every project, its location and its approved 360° photos without an account.

## Tech stack

| Layer | Used |
|---|---|
| Frontend (`client/`) | React 18, Vite 5, React Router 6, Tailwind CSS 3, Headless UI, lucide-react icons, react-day-picker, Chart.js + react-chartjs-2, Vitest |
| Map | Leaflet + react-leaflet with OpenStreetMap tiles; province boundary from OpenStreetMap (ODbL) |
| 360° viewer | Pannellum (equirectangular panoramas) |
| Backend (`server/`) | Node.js 22, Express 4, zod (validation), helmet, express-rate-limit, multer (uploads), sharp + image-size + exifr (photo compression, size, GPS / time), PDFKit (PDF reports), ExcelJS (Excel exports), node-cron (daily flag check), `node --test` + supertest |
| Database | Supabase: PostgreSQL with Row Level Security, Auth (email + password), Storage (private buckets) |
| Deployment | Dockerfiles for the API and the web app (nginx), `docker-compose.yml` |

## Features

### Public portal (no account needed)

| Page | What it shows |
|---|---|
| Dashboard (`/`) | Search box (project name or municipality), four live counters — Total projects, Ongoing, Completed, Delayed or stalled (delayed + suspended) — a full-width project map, and project cards with status and municipality filters |
| Projects (`/projects`) | Every project as a card, with search, status and municipality filters and paging |
| Project Map (`/map`) | Full-height map with a pin for every project that has coordinates, coloured by status |
| Project drawer | Opens from a pin or a card, sliding in from the right while the page stays usable: 360° viewer (or a placeholder when no photo has been published), location, implementing office, contractor, contract cost, status, progress and dates |

The public sees no flags, audit findings, finances, phases, documents or activity: the API never selects them and the database refuses them to the anonymous role. Only 360° photos that an Auditor or Admin has approved for the public are shown. Top navigation bar (no sidebar); **Sign in** is for staff.

### Staff workspace (`/app`, after sign-in and approval)

| Module | What it does |
|---|---|
| Dashboard | Totals and charts (flags, status, furthest behind schedule, flags per municipality, contract vs disbursed); findings assigned to the signed-in person |
| Project Management | Register, edit and view projects: office, contractor, location (map picker limited to the Occidental Mindoro boundary), approved budget, contract amount, Notice to Proceed and duration. The Project ID (e.g. `26OM0332`) is generated by the database. Admin can delete |
| Phases & progress | Weighted construction phases; overall completion = Σ(weight × accomplishment) ÷ Σ(weight), compared with the planned progress for today; progress report history |
| Finance | Obligations, disbursements, variation orders and expenses, by project and by phase; checks against the contract amount and the 10% variation-order limit |
| 360° images | Upload panoramas; the server reads GPS and capture time (EXIF), checks distance from the site, dates and reuse of the same file, and compresses large files. Offline queue sends photos when the connection returns. Auditors / Admin approve photos for the public |
| Automatic flags | Re-evaluated after every change and daily at 01:15 (Asia/Manila): status (Not started / Ongoing / Delayed / Completed) and a Green / Yellow / Red flag with reasons. Thresholds are editable in System Settings |
| Flags & Audit | Auditors confirm or override flags (override needs a reason and evidence), record findings with recommendations, assign them to DPWH personnel and follow the corrective action |
| Documents | Contracts, programs of work, reports, variation orders, payment documents and plans per project (PDF, image, Word, Excel; 25 MB) |
| Project Map | Flag-coloured markers with filters (municipality, barangay, office, contractor, status, flag) and a side panel with the latest 360° photo |
| Reports | Flagged-projects report (PDF / Excel), financial summary (Excel), one project's audit report (PDF) |
| Contractors / Offices & Agencies | Directories with an Actions column (edit, suspend / reactivate, delete with confirmation). Office types: District Engineering Office, Field Office, Other |
| User Management (Admin) | Approval queue for registrations (approve / reject with reason), create and edit accounts, suspend / lift suspension, delete accounts without records. The sidebar badge counts pending registrations |
| Activity Logs (Admin, Auditor) | Append-only record of every change |
| System Settings (Admin) | Flag thresholds; re-checks every project at once |
| My account | Photo, name, position, password |

## Roles and access

| Who | How they get in | What they can do |
|---|---|---|
| Public visitor | No account | Browse the public portal |
| DPWH Personnel | Registers on `/register`, then waits for approval | Register and edit projects, contractors, phases, progress, finances, photos, documents |
| Auditor | Registers on `/register`, then waits for approval | Review flags, record and publish findings, approve photos for the public, reports, activity log |
| System Administrator | Created or approved by another admin | Everything above plus User Management, offices, deletions and settings |

- Registration offers only **DPWH Personnel** and **Auditor**. The new account gets **no role**: `profiles.approval_status = 'pending'` and `requested_role` holds the choice.
- A pending (or rejected) account can sign in but sees only the public portal, with a banner showing its status. Every staff API route refuses it (`requireRole` also requires an approved account) and Row Level Security gives it no staff rows (`private.app_role()` returns a role only for active, approved accounts).
- The admin approves or rejects from **User Management → Access requests**. Approving grants the role (the requested one by default); rejecting records an optional reason. The database refuses a role on any account that is not approved.
- Writes go through the API with the service-role key, which never leaves the server. Reads run as the caller (or as the anonymous role for the public portal), so Row Level Security applies.

## Setup

### Prerequisites

- Node.js 22 or later (the server uses `node --env-file`)
- A Supabase project (this repository's live project is **IPMATS**)
- Optional: Docker Desktop, to run the containers

### Install

```powershell
npm run install:all
```

### Environment variables

`server/.env` (copy `server/.env.example`; never commit it):

| Variable | Example | Description |
|---|---|---|
| `SUPABASE_URL` | `https://your-project-ref.supabase.co` | Supabase project URL (required) |
| `SUPABASE_ANON_KEY` | `sb_publishable_xxx` | Publishable (anon) key; public-portal reads run with it (required) |
| `SUPABASE_SERVICE_ROLE_KEY` | `sb_secret_xxx` | Service-role key, server only. Without it the API is read-only (writes return 503) |
| `PORT` | `4000` | API port (default 4000) |
| `NODE_ENV` | `development` | `test` disables the daily flag job |
| `CORS_ORIGINS` | `http://localhost:5173` | Allowed browser origins, comma-separated (default `http://localhost:5173`) |
| `DAILY_FLAG_CHECK_CRON` | `15 1 * * *` | When the daily flag check runs (default 01:15) |
| `TZ_NAME` | `Asia/Manila` | Time zone of the daily check (default Asia/Manila) |
| `SIGNED_URL_TTL` | `3600` | Lifetime in seconds of signed links to private photos and files (default 3600) |

Used only by the scripts in `server/scripts/`: `API_URL` (default `http://localhost:4000/api`), `SEED_EMAIL`, `SEED_PASSWORD`, `SEED_ADMIN`, `SEED_AUDITOR` (demo accounts the scripts sign in with).

`client/.env` (copy `client/.env.example`; public values only — they are bundled into the browser):

| Variable | Example | Description |
|---|---|---|
| `VITE_SUPABASE_URL` | `https://your-project-ref.supabase.co` | Supabase project URL |
| `VITE_SUPABASE_ANON_KEY` | `sb_publishable_xxx` | Publishable key for sign-in |
| `VITE_API_URL` | `/api` | API base URL (Vite proxies `/api` to `http://localhost:4000` in development) |

`.env` in the root (copy `.env.example`; Docker only): `DOCKERHUB_USER` (image owner), `TAG` (image tag, default `week2`), `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`.

### Database migrations

There is no migration runner in this repository. Apply the files in `database/migrations/` **in numeric order** in the Supabase SQL Editor (or with the Supabase CLI / MCP). The IPMATS project already has `001`–`018` applied. Never edit or renumber a migration that has been applied; write a new one that changes or reverses it.

### Seed data (fictional demo data)

1. `database/seed/seed.sql` — municipalities, barangays, offices, demo accounts, contractors and projects (`npm run seed:generate` rebuilds it from `generate-seed.mjs`).
2. `database/seed/seed_week2.sql` — phases, monthly progress reports and financial records (`node database/seed/week2-seed.mjs` rebuilds it).
3. With the API running, in `server/`: `npm run seed:images` uploads placeholder 360° panoramas (labelled "SAMPLE – NOT A REAL PHOTO") through the upload API.

Demo accounts (password `Dpwh360!Demo2026`; change or delete them before real use): `admin@dpwh360.local` (System Administrator), `personnel@dpwh360.local` and `personnel.south@dpwh360.local` (DPWH Personnel), `auditor@dpwh360.local` (Auditor), `applicant@dpwh360.local` (pending registration).

### Run in development

```powershell
npm run dev:server
```

```powershell
npm run dev:client
```

Open <http://localhost:5173>. Other commands: `npm test` (server and client tests), `npm run build` (production build of the web app), `npm run flags:recheck` in `server/` (re-check every project's flag now).

### Docker

```powershell
docker compose up --build
```

The web app is served on <http://localhost:8080> by nginx, which forwards `/api` to the API container. The API reads `server/.env` at run time; no secret is stored in an image.

## Database

| Table / view | Holds |
|---|---|
| `municipalities`, `barangays` | The 11 municipalities and their barangays (lookup) |
| `agencies` | Implementing offices (type: district engineering office, field office, other) |
| `profiles` | One per Auth user: role (null until approved), requested role, approval status, office, suspension |
| `contractors` | Contractors, PCAB licence, contacts, active flag |
| `projects` | Project records, location, budget, contract, schedule, status, automatic flag |
| `project_phases`, `progress_updates` | Weighted phases and progress report history |
| `financial_records` | Obligations, disbursements, variation orders, expenses |
| `site_images` | 360° photos (files in the private `panoramas` bucket), GPS / time checks, public approval |
| `flag_history`, `flag_reviews` | Automatic flag history and auditor decisions (append-only) |
| `audit_findings` | Findings, recommendations, assignment and corrective actions |
| `project_documents` | Supporting documents (private `project-documents` bucket) |
| `activity_logs` | Who did what and when (append-only) |
| `system_settings` | Flag thresholds |
| `v_project_summary` | Staff view: project with names, progress, finance totals and flags |
| `v_public_projects` | Public view: only the columns the portal shows, no flags or finances |

Migrations are numbered in the order they were applied: `001`–`006` Weeks 1–2 and the first public portal, `007`–`011` Week 3 and later improvements, `012` office status, `013` and `014` a data-provenance experiment and its reversal, `015` office restructure, `016` reopens the public portal to the anonymous role (reverses `006`), `017` removes the Public role and adds admin approval, `018` fixes the sign-in ban set by `017`.

## Known limitations and unfinished work

- No 360° photo is currently approved for the public, so every public drawer shows the placeholder until an Auditor or Admin approves photos.
- All project, contractor and photo data is fictional demo data; the uploaded panoramas are drawn placeholders.
- Registration needs email confirmation. Without custom SMTP, Supabase sends only a few emails per hour.
- The public account `public@dpwh360.local` from the old model is kept but deactivated; pending accounts have no "My account" page until they are approved.
- `server/scripts/seed-sample-project.mjs` mentions `npm run seed:sample`, which does not exist; run it with `node --env-file=.env scripts/seed-sample-project.mjs` from `server/`.
- There are no end-to-end browser tests; the automated tests cover the API guards, validation rules, flag rules, exports and a few client helpers.
